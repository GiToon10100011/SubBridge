# ADR-003: 프로젝트 저장 구조

- 상태: 제안
- 날짜: 2026-11-02

## 맥락
요구사항 예시는 `project.json` + `subtitles/*.srt` + `metadata/corrections.json`이었다. 자동 저장, 크래시 복구, 수천 줄의 부분 갱신, undo가 필요하고, 오디오와 프로젝트는 독립적으로 관리되어야 한다.

## 선택지
| 방식 | 장점 | 단점 |
|---|---|---|
| 파일 기반 (JSON + SRT) | 사람이 열어볼 수 있다 | 원본이 여러 곳으로 갈린다. 부분 갱신·원자성·undo 이력이 약하다. 크래시 중 파일이 깨질 수 있다 |
| **프로젝트당 SQLite 한 파일** | 트랜잭션, 부분 갱신, 인덱스, 이력 테이블 | 사람이 직접 읽기 어렵다 (→ 내보내기로 해결) |
| 전역 단일 DB | 프로젝트 목록이 쉽다 | 프로젝트 이동/백업/삭제가 어렵다 |

## 결정
**프로젝트 = 폴더 1개**, 그 안의 **`project.db`(SQLite, WAL)가 유일한 원본**이다. 오디오는 `audio/` 폴더에 별도 파일로 두고 완료 시 폴더째 지운다. SRT/VTT는 저장 형식이 아니라 **내보내기 산출물**이다. JSON은 백업·교환용으로만 쓴다. 앱 전역 DB는 최근 프로젝트와 모델 목록만 가진다.

설정:
- `journal_mode=WAL`, 일반 편집은 `synchronous=NORMAL`. 상태 전이와 오디오 삭제 단계 기록은 `FULL`.
- `rusqlite`(번들 SQLite)를 전용 DB 스레드에서 실행.
- 저장 위치는 `~/Documents/SubBridge/` (Caches는 OS가 비울 수 있다).

## 결과
- 편집 1건 = 트랜잭션 1건 → 자동 저장과 크래시 안전성.
- 오디오 삭제와 프로젝트 보존이 파일 수준에서 자연스럽게 분리된다.
- `.lock` + 하트비트로 비정상 종료를 감지한다.
- 스키마 마이그레이션 정책(DATA_MODEL §4)이 필요하다.

## 주의
`synchronous=NORMAL`은 앱 크래시에는 안전하지만 전원 차단 시 마지막 트랜잭션을 잃을 수 있다. 이 점을 UI/문서에 숨기지 않는다.
