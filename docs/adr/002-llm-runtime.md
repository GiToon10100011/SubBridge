# ADR-002: 로컬 번역 LLM 런타임

- 상태: **채택** (Q5: 사용자가 「상관없음」으로 위임 → 권고안 채택, 2026-11-02)
- 날짜: 2026-11-02

## 맥락
원칙 1(여러 프로그램 설치를 요구하지 않는다)과 원칙 5·6(무료 로컬 기본, 교체 가능)을 만족하면서, 번역 서버가 죽어도 캡처가 계속되어야 한다.

## 선택지
| 방식 | 장점 | 단점 |
|---|---|---|
| Ollama 필수 | 모델 관리가 쉽다 | 별도 설치 → 원칙 1 위반. 데스크톱 앱 라이선스 논란 보도 ◐ |
| **llama.cpp `llama-server` 사이드카 번들** | 설치 불필요. 프로세스 분리(죽어도 캡처 유지). OpenAI 호환 API | 번들 크기 증가, 모델 다운로드/관리를 직접 구현 |
| `llama-cpp-2` 크레이트로 프로세스 내 임베드 | 프로세스 하나 | semver 미준수라 버전 고정 필요, LLM 크래시가 앱을 끌고 감 |
| 클라우드 API | 품질 | 비용·프라이버시, 원칙 5 위반(기본값으로는) |

## 결정
**`llama-server`를 사이드카로 번들**하고, TranslationProvider는 **OpenAI 호환 API 하나**로 추상화한다. 이렇게 하면 같은 Provider로 번들 서버 · 사용자가 설치한 Ollama · 클라우드를 모두 연결할 수 있다.
Ollama는 **선택 Provider**로 남긴다 (이미 쓰는 사용자를 위해).

## 결과
- LLM 프로세스 장애는 캡처·ASR에 영향을 주지 않는다 (서킷 브레이커 + 자동 재시작).
- Tauri `bundle.externalBin` + `.spawn()`으로 띄우고 `CommandChild` 핸들을 유지한다 ◐.
- llama.cpp(MIT)의 고지 의무를 지킨다. 모델별 라이선스는 레지스트리에서 표시한다 (Hunyuan 계열·NLLB 제외).
- v0.2에서 Apple Translation(macOS 26+)을 같은 Provider 인터페이스의 다른 구현으로 추가한다.

## 열린 질문
Q1(배포 범위 → 허용 모델), Q4(최저 하드웨어), 실시간 ASR과의 GPU 경합 ❓.

## 자체 번역 엔진 (Q1, 2026-11-02 추가)

사용자가 자체 번역 엔진을 개발할 가능성이 크다고 밝혔다. 엔진 형태는 미정이다. 이 결정(OpenAI 호환 Provider + 사이드카)은 그대로 유효하고, 자체 엔진은 다음 중 하나로 붙인다.

- **로컬 모델**: GGUF로 변환해 같은 llama-server 사이드카에 올린다. 기반 모델의 라이선스를 상속한다 (TECH_STACK §8).
- **서버/API**: 같은 OpenAI 호환 Provider 또는 전용 Provider로 연결한다. 원칙 5와 충돌하므로 옵트인으로만 켠다.

TranslationProvider 계약은 PIPELINE §6.1, 위험은 RISK_ANALYSIS R12.
